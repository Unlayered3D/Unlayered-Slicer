# Bridge actions: the automation catalog

An embedded web application (WEB_APP_BRIDGE.md) can ask the slicer to do what a person does with
menus, toolbars, gizmos, the sidebar and the settings tabs. Every such capability is described once,
in a C++ **action catalog**; the bridge lists it (`slicer.listActions`), runs it
(`slicer.invokeAction`), and a coverage script checks it against every control in the GUI sources,
so a new menu item cannot be forgotten.

WebAppBridge.cpp has one hook, every line of it marked `Actions:`.

## One source of truth, two kinds of entry

- **Actions** have a runner and are called through `slicer.invokeAction {id, target, params}`. Most
  menu-shaped verbs (mirror, clone, add a modifier, delete a plate, run a calibration) are actions.
- **Typed methods** carry `bridge_method`. Rich inputs and structured outputs (settings, the model
  tree, painting selectors, cut planes) keep their own method. A typed-method descriptor without a
  runner describes a method WebAppBridge.cpp serves; one with a runner is a new typed method that
  WebAppBridgeActions dispatches (the reply is the runner's result as-is).

`slicer.listActions` shows a typed-method entry only while its method is in the tab's
`capabilities`, so a method behind a permission that is off, or from code that is not built, is
never advertised.

No translation unit registers itself: libslic3r_gui is a static library and an unreferenced
self-registering object would be dropped by the linker. `register_all()` calls each domain function
explicitly. Register functions build descriptors and store lambdas only; they never touch the GUI,
so the catalog builds in unit tests.

## Descriptor

`id` (`<domain>.<verb>`, lowerCamel, stable once shipped), `label` (the untranslated UI string),
`summary` (one sentence, no product names), `risk`, `gate`, `confirm`, `target`
(`{kind: objects|object|volumes|volume|instances|plate|none, required, accepts?}`; `accepts` lets an
object action also take `volumes` and/or `instances`, see below), `params` (schema),
`effects` (geometry, structure, settings, presets, plates, project, view, file, printer, paint,
selection), `long_running` / `timeout_ms` (≤ 50 s, inside the page shim's 60 s), `ui` (manifest keys
it implements), `examples` (≥ 1 for a runnable action; each must validate), `bridge_method`, `since`.

`Catalog::add` refuses a duplicate or malformed id, a forbidden domain (plugins, account, login,
tokens, process execution, app lifecycle, firmware), a schema outside the dialect, an unknown effect
and an example that does not validate. The catalog version is a 64-bit FNV-1a digest of every
descriptor's JSON, so the server caches the catalog by it.

## Params dialect

`type` (object, string, number, integer, boolean, array), `enum`, `minimum`/`maximum`,
`minLength`/`maxLength` (code points), `minItems`/`maxItems`, `items`, `properties`, `required`,
`additionalProperties: false` (mandatory on every object), `description`, `default`, and
`x-exactlyOne: [[names], [names]]` for either/or groups. Nothing else. Defaults fill absent
properties before validation, never an `x-exactlyOne` alternative.

The dialect has no free-form maps. Where an action takes settings, they travel as a list of pairs,
`values: [{key, value}]`, each value a string in the option's text (.ini) form (`"6"`, `"60%"`,
`"0.2,0.2"`), exactly as `slicer.getSettings` reports it; `remove: [key]` lists keys to drop. The
typed `slicer.setSettings` keeps its `{key: value}` object, which it validates itself. Every invoke is validated in the
slicer, whatever the page claims to have checked.

## Targets and the selection

A target names objects, volumes (parts) and instances by `{id}` (the `ObjectID` the model tree
reports; it survives edits to other objects), `{index}` or exact `{name}`, plus a plate index, or
`selection: true` for what the person has selected. A plate with one object implies it. The runtime
resolves the target, then **selects** it, and the runner calls the same Plater / ObjectList function
the menu item calls, which acts on the selection. That reuses the GUI's own snapshots, list refresh
and plate refiling instead of duplicating them.

An object action whose menu item also works on a part or on one instance (Mirror, Center, Drop,
Order, Printable, Remove instance) declares `target.accepts: ["volumes"|"instances"]` beside its
`kind: "objects"`. A target naming only parts or instances then satisfies `required`, and the runner
acts on exactly what was named. Pages that read only `kind` keep working; the summary says what else
the action takes.

## Invoking

1. The settings permission and the action's gate; a missing runner (a typed method) is refused.
2. Params: defaults, then validation (`1002` with `data.path`, `data.needs`).
3. Guards: a modal dialog (`1007`); for anything but Read / Ui: an open gizmo (`1007`,
   `data.gizmo`), background slicing, a running plate job.
4. The target, then the action's enabled predicate (`1016`, `data.reason`).
5. The runner. A synchronous result is answered as `{status: "done", result, effects, undo}`.
   A long-running one returns `started()` and finishes a `Deferred`; the bridge waits up to the
   action's timeout and otherwise answers `{status: "running", jobId}` and reports the end as
   `slicer.actionFinished`.

`listActions` computes `enabled` / `disabledReason` live from the same guards and predicates.

### Writing an action

- An action about an open gizmo itself (closing it) sets `allow_with_gizmo`; every other
  non-Read action is refused while a gizmo is open.
- One `ctx.snapshot()` before a Mutate runner changes anything; it is named
  "<label> (automated)". Never confirm an undoable model edit.
- Never open a modal dialog. Where the menu item asks for something (a count, a name, a file),
  that is a param; where it asks for a file, it is a `url` fetched with `host->download`.
- Destructive: `ctx.confirm({title, message naming exactly what is lost, details, accept_label})`,
  and `WAB_USER_CANCELLED` with nothing changed when declined. Skip the confirmation only when
  nothing would be lost (say so in `confirm_skip_rule`).
- Replacing the project: `ctx.project_dirty_preflight`; switching a preset:
  `ctx.preset_switch_preflight(type, target)` (covers the dependent presets);
  `ctx.preset_dirty_preflight(type)` when edits would be lost without a switch. They implement `ifProjectDirty` (`ask` → `1013 {projectDirty}`,
  `save`, `discard`, `prompt`) and `ifDirty` (`ask` → `1013 {dirty, dirtyKeys, dirtyTypes}`, `discard`, `save`, `transfer`, `prompt`;
  a switch covers the dependent presets too -- docs/bridge-actions/presets.md).
- Plater jobs: `return ctx.after_plate_jobs([](InvokeContext& c, bool timed_out) {...});`.
- Results refer to objects with `object_ref_json` / `volume_ref_json` so the page can follow ids.

## Safety

| Risk | Confirmation |
|---|---|
| Read, Ui | none |
| Mutate | none: undo is the safety net |
| Destructive | native confirmation naming what is lost, unless nothing would be |
| OutwardFile | the native Save dialog (the person picks the path); overwriting the open project is confirmed |
| OutwardNetwork | allow-listed hosts only (openProjectFromUrl's rules) and a native confirmation |
| OutwardPrinter | the printer permission (off by default) and the printer family's own confirmations |

Not in the catalog at all: sign-in and tokens, print-host credentials, privacy and diagnostics
choices, plugins, process execution and opening paths, quitting or restarting, firmware and update
installs, application settings outside an allowlist. A page cannot press, pre-answer or see the
native dialogs. Starting a cloud slicing run is not automatable; a page may only preselect a mode.

The dev edition reads `UNLAYERED_E2E_AUTOCONFIRM=accept|cancel` and `UNLAYERED_E2E_SAVE_DIR` so the
end-to-end tests run unattended, and logs every automatic answer. A customer build never reads them.

## Turns and undo

A page sends the same `turn` id on every call one user request causes. `RequestScope` wraps every
bridge request: for a request carrying `params.turn` it records the undo-stack snapshots that appeared
while it ran (typed methods included), and the `settingsChanged {source: "bridge"}` notification of a
write records `(type, preset, key, previous, written)`. A key written twice keeps its first previous.
Runners that write the project configuration (filament colours, flush volumes, bed type), which is
not on the undo stack, record those writes themselves as type `project`.

`slicer.undoTurn {turn}` rolls the undo stack back to before the turn's first snapshot, only while its
last snapshot is still the newest one and the stack is at its top (otherwise `1013 {laterEdits}`:
the person edited since, and their edit is not undone with it). It then puts back each written
setting whose current value is still the one the turn wrote, in the same preset; the others are
listed in `skipped`. A turn is forgotten once undone; at most 64 are remembered per tab.

`edit.undo` / `edit.redo` step the stack as the Edit menu does and are not part of any turn.

## Coverage gate

`tools/check_action_coverage.py` scans `src/slic3r/GUI` for `append_menu_*` / `append_submenu`
calls (the label is the first `_L(...)` before any accelerator; computed labels are keyed by
expression and enclosing function), `SideButton`s, main-toolbar items, gizmos, gizmo ImGui buttons,
Preferences rows, settings-tab buttons and sidebar control bindings. A key is
`<file>::<kind>::<label|member>`; duplicates in one file fold. Each key lives in exactly one manifest
with one of `{action}`, `{actions: [...]}`, `{coveredBy: <method or id>}`, `{excluded: <reason>}`
(forbidden-security, os-dialog-replaced, cosmetic-help, duplicate-alias, sla-only, hidden-dead,
deferred-printer, not-allowlisted) or `{todo: true}`. It fails on an unmapped key, an unknown reason, or an action id
the catalog snapshot lacks; `--strict` also on `todo` and stale keys. `--init-manifests` adds new
keys as `todo` under the domain that owns their file and label. The Catch2 test
`[actions][manifest]` checks the same ids without Python.

## Tests

- Catch2 `[actions]` (slic3rutils): ids, dialect, examples, confirmation rules, forbidden domains,
  manifest ids, the snapshot (`UPDATE_SNAPSHOT=1` rewrites it), the schema vectors, the turn log
  and target resolution.
- `tools/bridge_e2e`: `run_e2e.ps1` seeds a separate data directory and WebView2 folder, starts a
  dev-edition slicer with the second web slot on the driver's page, runs `cases/*.yaml` and the
  generic per-action test (for each runnable action with an example: snapshot the plate, the model
  tree and the print settings, invoke under a turn, check the declared effects, `undoTurn`, check
  the snapshot is back; destructive and outward actions run once with auto-cancel, expecting `1006`
  and no change, and once with auto-accept), and stops the slicer by PID.
